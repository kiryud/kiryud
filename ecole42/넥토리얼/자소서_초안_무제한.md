## 1. 이번 넥토리얼에 지원한 동기와 게임 프로그래머가 되기 위해 노력해온 과정을 서술해 주세요.

**[납득할 수 있을 때까지 파고드는 개발자, 넥슨의 근본을 향하다]**
상용 게임 엔진은 훌륭한 도구지만, 저는 "근거 없는 코드는 신뢰할 수 없다"는 철학을 가지고 있습니다. 기성 툴이나 라이브러리를 사용할 때도 그 내부가 어떻게 동작하는지 납득할 수 있어야만 직성이 풀립니다. 수십 년간 대한민국 게임 서버의 근간을 다지고, 자체 엔진과 대규모 트래픽 아키텍처의 표준을 만들어온 넥슨은 표면적인 API 조립을 넘어 시스템의 밑바닥부터 집요하게 파고들어야 하는 기술의 명가입니다. 동작 원리를 뜯어보고 납득할 때까지 파고드는 제 개발 철학을 가장 완벽하게 증명할 수 있는 곳이기에 넥토리얼에 지원했습니다.

**[엔진의 블랙박스를 벗어난 3D 멀티플레이 구현: tini-pong]**
게임 프로그래밍의 본질을 이해하기 위해, 저는 유니티 대신 웹 브라우저 환경에서 SPA 기반의 3D 실시간 온라인 멀티플레이어 게임 `tini-pong`을 직접 개발했습니다. 
상용 엔진의 컴포넌트 없이, JavaScript와 Three.js를 활용해 그래픽스 렌더링 파이프라인을 직접 통제했습니다. 공간의 좌표계 변환, 빛의 반사, 3D 객체의 배치를 코드로 깎아내며 엔진이 대신해 주던 그래픽스의 근본 원리를 체득했습니다. 여기에 더해 WebSocket(wss)을 연동하여 실시간 멀티플레이 환경을 구축하며, 네트워크 지연 환경에서 클라이언트가 서버와 어떻게 실시간으로 데이터를 주고받으며 동기화되는지를 몸소 부딪치며 파악했습니다.

**[가설과 검증, 그리고 스스로 증명하는 몰입]**
제가 이토록 본질에 집착하는 이유는, 타인이 떠먹여 주는 지식에 기대지 않고 스스로 가설을 세워 시행착오를 통해 증명해 온 저만의 학습 철학 때문입니다. 코드가 어떻게 동작해야 하는지 먼저 논리적으로 가설을 세우고, 납득할 수 있을 때까지 문서를 뒤지며 실험하는 과정을 통해 저만의 확고한 개발 기준을 정립해 왔습니다.
이러한 철학을 안고 42seoul에 합류했을 때, 교수자도 교재도 없이 밑바닥부터 시스템을 깎아내야 하는 환경은 제게 완벽한 몰입의 무대였습니다. 막막한 블랙박스 앞에서도 흔들리지 않고 공식 문서(RFC)와 OS 구조를 뜯어보며 단서를 찾고 원인을 추적하는 집요함. 넥슨의 게임 로직에서 치명적인 버그가 발생하더라도, 저는 당황하지 않고 가설을 세운 뒤 명확한 근거를 찾을 때까지 파고들어 문제를 해결하는 끈질긴 엔지니어가 될 것입니다.

## 2. 본인이 참여했던 프로젝트(개인·팀 무관) 하나를 선택해 설명하고, 가장 어려웠던 문제를 어떻게 해결하였는지 결과와 함께 구체적으로 서술해 주세요.

**[C++98 환경에서의 데이터 관리 및 명령어 처리 아키텍처 설계]**
제 개발 역량의 뼈대를 완성한 프로젝트는 42seoul에서 순수 C++98 표준으로 다중 접속 채팅 서버를 구축한 `ft_irc`입니다. 저는 이 프로젝트에서 단일 IRC 서버의 핵심인 **'데이터 관리 및 명령어 처리 설계와 구현'**을 전담했습니다. 스마트 포인터나 최신 STL 컨테이너의 강력한 기능을 사용할 수 없는 제약 속에서, 수많은 클라이언트와 채널 간의 복잡한 상태를 안전하게 관리해야 하는 난관에 직면했습니다.

**[마주한 위기: 객체 간의 복잡한 의존성과 메모리 관리의 한계]**
가장 큰 문제는 서버 내부에 존재하는 수많은 '유저(Client)'와 '채널(Channel)' 객체 간의 복잡한 N:M 다대다 관계였습니다.
채팅 서버의 특성상 하나의 유저는 여러 채널에 속할 수 있고, 하나의 채널 역시 다수의 유저 포인터를 보유해야 합니다. 유저가 특정 채널을 떠나거나(PART), 서버 접속을 완전히 종료(QUIT)할 때, 관련 메모리를 정확하게 해제하지 않거나 리스트에서 포인터를 삭제하지 않으면 즉시 당글링 포인터(Dangling Pointer)가 발생하여 서버가 다운되거나, 반대로 지우지 못한 채널 정보로 인해 심각한 메모리 누수(Leak)가 발생했습니다.

**[해결 과정: 철저한 소유권 규칙 수립과 예외없는 리소스 반환]**
문제 해결을 위해 저는 '근거 없는 코드는 작성하지 않는다'는 철학에 따라, 서버 내부의 데이터 흐름과 소유권(Ownership) 모델을 완전히 뜯어고쳤습니다.
1. **명확한 소유권(Ownership) 분리와 참조 관리:** 객체의 생성과 소멸을 전담하는 매니저 클래스를 별도로 두어, 유저와 채널 객체의 실제 메모리 소유권을 중앙 집중화했습니다. 유저가 접속을 종료할 경우, 해당 유저가 속한 모든 채널 객체들을 순회하며 자신을 가리키는 얕은 포인터 참조들을 일괄적으로 지워버리는 연결 해제(Decoupling) 로직을 명령어 처리 흐름에 엄격하게 이식했습니다.
2. **프로토콜 파싱 및 명령어 처리의 캡슐화:** 클라이언트로부터 수신되는 가변적인 IRC 원시 텍스트 데이터를 안전하게 파싱하기 위해, 문자열을 `\r\n` 기준으로 분리하고 각 명령어(JOIN, PRIVMSG 등)의 인자(Arguments)를 검증하는 독립적인 파서 모듈을 구축했습니다.
3. **누수 없는 메모리 통제:** `valgrind`와 `leaks`를 활용해 극한의 테스트를 반복하며, 명령어 처리 중 예외가 발생하여 함수를 빠져나가는 모든 에러 핸들링 분기점마다 메모리가 정상 반환되도록 코드를 다듬었습니다.

**[결과 및 성과]**
그 결과, 다수의 유저가 동시에 입장과 퇴장을 반복하고 텍스트를 난사하는 스트레스 상황에서도 단 1바이트의 누수나 포인터 참조 오류가 발생하지 않는 견고한 데이터 처리 로직을 완성할 수 있었습니다. 넥슨의 라이브 서버에서 어떠한 복잡한 상태 데이터가 오가더라도, 저는 객체의 생명 주기를 완벽히 통제하고 엣지 케이스를 방어해 낼 확고한 기본기를 갖추었습니다.

## 3. 협업과정에서 반대 의견이나 솔직한 피드백을 전해야 했던 경험을 떠올려, 당시 어떻게 행동했고, 그 경험을 통해 무엇을 배웠는지 구체적으로 서술해 주세요.

**[좋은 질문으로 납득을 이끌어내는 협업]**
저는 누군가와 함께 일할 때 "서로가 무엇을 하고 있는지 명확히 인지해야 한다"는 원칙을 지킵니다. 좋은 대답은 언제나 '좋은 질문'으로부터 나온다고 굳게 믿기 때문입니다. 42seoul의 엄격한 동료 평가(Peer Review)와 `tini-pong`과 같은 팀 프로젝트를 거치며, 저는 이견이 발생했을 때 감정적 반대가 아닌 '명확한 근거와 질문'으로 문제를 조율하는 법을 배웠습니다.

프로젝트를 진행하며 팀원과 구현 방식이나 코드의 설계(Architecture)를 두고 의견이 충돌할 때가 있었습니다. 팀원은 당장의 빠른 구현을 위해 하드코딩이나 특정 방식의 데이터 처리를 선호했지만, 저는 그것이 향후 확장성이나 메모리 안전성 측면에서 리스크가 될 수 있다고 판단했습니다.
이때 저는 "그 방식은 틀렸다"고 무작정 반대하는 대신, 코드가 궁극적으로 어떤 동작을 해야 하는지 근본적인 **질문**을 던졌습니다. "만약 이 모듈에 예기치 않은 형태의 데이터가 들어오면 예외 처리는 어떻게 동작하게 될까?", "이 로직이 멀티 클라이언트 환경에서도 안전하게 메모리를 반환할 수 있을까?" 등 스스로 문제점을 객관화할 수 있는 질문을 구성했습니다.

동시에, 제가 제안하는 방식이 왜 더 나은지 입증하기 위해 공식 레퍼런스나 테스트 코드를 작성하여 근거를 제시했습니다. 팀원은 제 질문을 통해 스스로 로직의 빈틈을 발견했고, 우리는 기분 상하는 일 없이 자연스럽게 가장 안정적인 아키텍처로 합의를 이룰 수 있었습니다.
이 경험을 통해 저는 협업에서의 솔직한 피드백이란, 단순히 문제점을 지적하는 것이 아니라 '상대방이 납득할 수 있는 좋은 질문을 통해 스스로 최선의 결론에 도달하도록 돕는 과정'임을 배웠습니다. 넥슨의 개발 현장에서도 저는 항상 진행 상황을 투명하게 알리고, 날카롭고도 좋은 질문을 던져 팀의 코드를 견고하게 만드는 개발자가 되겠습니다.

## 4. 현재 자신 있게 활용할 수 있는 핵심 역량(프로그래밍 언어, 게임 엔진, AI 활용 능력 등)을 실제로 활용했던 사례와 함께 서술해 주세요.

**[메모리 제어부터 실시간 웹 그래픽스까지, 게임의 뼈대를 짜는 역량]**
저의 핵심 역량은 추상화된 프레임워크나 엔진의 가호 없이, 프로그램이 구동되는 가장 밑바닥의 메모리부터 화면에 그려지는 그래픽스의 원리까지 코드로 직접 제어해 본 끈질긴 '로우레벨 엔지니어링 역량'입니다.

**첫째, C/C++ 기반의 1바이트 오차도 허용하지 않는 엄격한 메모리 제어 역량입니다.**
`minishell` 프로젝트에서는 복잡하게 얽힌 프로세스 생성(`fork`, `execve`)과 시그널 제어 과정에서 단 하나의 메모리 누수도 발생하지 않도록 정확한 동적 할당과 해제 사이클을 통제했습니다. `ft_irc` 프로젝트에서는 수많은 유저와 채널 객체가 얽힌 다대다(N:M) 구조 속에서 객체의 소유권을 완벽하게 분리하여 당글링 포인터를 근절했습니다. 엔진이 메모리를 대신 관리해 주지 않는 환경에서 극한까지 훈련된 이 제어력은, 넥슨의 코어 아키텍처 단에서 발생하는 미세한 퍼포먼스 저하를 잡는 데 즉각적으로 활용될 수 있습니다.

**둘째, JavaScript와 Three.js, WebSocket을 융합한 3D 멀티플레이 구현 역량입니다.**
상용 멀티플레이 플러그인 없이 `tini-pong`을 개발하며, SPA 환경에서 WebSocket을 띄워 실시간 온라인 퐁(Pong) 게임을 만들었습니다. 클라이언트 간의 네트워크 레이턴시를 고려해 데이터를 주고받고, Three.js를 다루며 공간 좌표와 그래픽스 렌더링 파이프라인의 기초를 체득했습니다.

엔진의 사용법을 외우는 것은 며칠이면 되지만, 엔진이 작동하는 근본 원리(메모리 구조, 네트워크 동기화, 렌더링 기초)를 몸으로 부딪쳐 체득한 기본기는 결코 쉽게 얻을 수 없습니다. 넥슨의 어떤 복잡한 자체 기술 스택 앞에서도, 저는 이 거친 기본기를 바탕으로 납득할 때까지 파고들어 시스템을 통제해 낼 자신이 있습니다.
