## 1. 이번 넥토리얼에 지원한 동기와 게임 프로그래머가 되기 위해 노력해온 과정을 서술해 주세요. (1,000자)

**[엔진 밖에서 게임의 본질을 조립하다]**
게임을 플레이하는 것보다, 게임이 화면에 그려지고 수많은 유저가 하나의 세계에서 동기화되는 '원리'를 파헤치는 것에 더 깊은 희열을 느낍니다. 넥슨은 자체 엔진을 유지보수하고 압도적인 트래픽의 라이브 서버를 지탱하는, 국내에서 가장 깊은 기술적 근간(Core)을 가진 게임사입니다. 만들어진 툴을 조립하는 양산형 개발자가 아니라, 툴이 작동하는 밑바닥 로직부터 통제하길 원하는 제 개발 철학과 가장 완벽하게 맞닿아 있는 곳이기에 주저 없이 넥토리얼에 지원했습니다.

**[렌더링부터 네트워크 동기화까지: Full-Cycle 멀티플레이 구현]**
저는 상용 게임 엔진(Unity/Unreal)의 편리함에 기대지 않고, 게임 프로그래밍의 본질을 맨바닥부터 부딪치며 체득해 왔습니다. 그 치열한 노력의 결과물이 실시간 3D 멀티플레이어 게임 `tini-pong`입니다. 
웹 브라우저 환경에서 게임을 구동하기 위해 Three.js를 활용하여 빛의 반사와 공간 좌표 등 3D 렌더링 파이프라인을 직접 제어했습니다. 그래픽스 로직을 구현하는 것을 넘어, 멀티플레이 환경을 구축하기 위해 WebSocket 기반의 실시간 네트워크 동기화(Sync) 로직을 파이썬으로 직접 설계했습니다. 
엔진의 '멀티플레이어 플러그인'을 쓰면 클릭 몇 번으로 끝날 일이었지만, 저는 직접 소켓 통신을 열고 클라이언트 간의 네트워크 지연(Latency)과 상태 불일치 문제를 마주했습니다. 프레임 보간과 데이터 패킷 구조를 논리적으로 뜯어고치며 해결하는 과정은 고통스러웠지만, 이를 통해 게임 루프(Game Loop)와 네트워크 동기화의 본질적인 작동 원리를 완벽하게 제어하는 '진짜 게임 프로그래머'의 시각을 갖추게 되었습니다.

과거, 불가피하게 가업(청소업)에 뛰어들어 주야를 가리지 않는 육체노동을 해야 했던 시절이 있었습니다. 육체의 한계가 오는 극한의 상황에서도 저는 매일 4권 이상의 책을 읽으며 사유의 끈을 놓지 않았고, 42seoul이라는 혹독한 환경에 던져졌을 때 남들이 상상할 수 없는 절박함으로 코딩에 몰입했습니다. 
어떠한 악조건 속에서도 포기하지 않고 가설을 세워 돌파구를 찾는 이 '독종' 같은 몰입력은, 상용 엔진의 블랙박스를 벗어나 렌더링과 소켓 통신의 원리를 파고드는 저만의 무기가 되었습니다. 넥슨의 코어 시스템과 라이브 서버 어딘가에서 발생하는 그 어떤 치명적인 버그라도, 끝까지 물고 늘어져 원인을 규명하고 해결해 내는 끈질긴 개발자가 되겠습니다.

## 2. 본인이 참여했던 프로젝트(개인·팀 무관) 하나를 선택해 설명하고, 가장 어려웠던 문제를 어떻게 해결하였는지 결과와 함께 구체적으로 서술해 주세요. (1,000자)

**[스마트 포인터 없는 C++98, 메모리와 동시성의 지옥을 통제하다]**
가장 큰 기술적 벽에 부딪혔던 경험은 42seoul에서 진행한 `ft_irc` 프로젝트입니다. 최신 문법과 STL의 편리함, 심지어 스마트 포인터조차 허용되지 않는 엄격한 C++98 표준 환경에서 외부 라이브러리 없이 순수 BSD 소켓만으로 다중 접속 채팅 서버를 구축해야 했습니다.

**[위기: 좀비 포인터(Dangling)와 메모리 릭의 위협]**
가장 큰 난관은 클라이언트들의 갑작스러운 접속 종료(Disconnect) 시 발생하는 메모리 관리와 동시성 제어였습니다. 유저(Client) 객체는 전체 접속자 목록뿐 아니라 여러 채널(Channel)에 중복 참조되어 있었습니다. 모던 C++의 `std::shared_ptr`가 없었기에, 유저가 접속을 끊을 때 해당 포인터를 완벽히 회수하지 않으면 서버 전체가 당글링 포인터(Dangling Pointer)에 접근해 Segfault로 다운되거나 심각한 메모리 릭(Leak)이 발생했습니다. 또한, `epoll/select` 기반의 논블로킹 I/O 멀티플렉싱 환경에서 끊임없이 들어오는 패킷을 단일 스레드로 처리하다 보니, 삭제된 메모리에 다른 이벤트가 접근하려는 레이스 컨디션 유사 문제가 빈발했습니다.

**[해결: 소유권 설계와 끈질긴 메모리 추적]**
문제를 해결하기 위해 막연한 구글링이 아니라, 객체의 생명 주기(Lifecycle)와 소유권(Ownership)에 대한 명확한 가설을 세우고 시스템 구조를 뜯어고쳤습니다.
첫째, 옵저버(Observer) 패턴과 유사한 구조를 직접 구현하여, 클라이언트의 접속이 끊어질 때 자신이 속한 모든 채널과 매니저 클래스에 즉각적으로 해제 이벤트를 전파하고 포인터를 nullptr로 초기화하도록 연결을 느슨하게(Decoupling) 설계했습니다.
둘째, 예외(Exception)가 발생하는 모든 에러 핸들링 분기마다 리소스가 안전하게 반환되도록 수동 RAII 패턴을 직접 구현했습니다. 
셋째, `valgrind`와 `leaks` 툴을 활용해 매 테스트마다 메모리 덤프를 분석하며, 단 1바이트의 누수도 허용하지 않을 때까지 코드의 메모리 할당/해제 흐름을 집요하게 추적했습니다.

이 가혹한 프로젝트를 통해, 저는 가비지 컬렉터나 스마트 포인터의 추상화 뒤에 숨겨진 '메모리의 진짜 생사(Life Cycle)'를 완벽하게 통제하는 능력을 얻었습니다. 게임 서버의 대규모 트래픽 속에서도 결코 무너지지 않는 견고한 아키텍처를 설계할 자신이 있습니다.

## 3. 협업과정에서 반대 의견이나 솔직한 피드백을 전해야 했던 경험을 떠올려, 당시 어떻게 행동했고, 그 경험을 통해 무엇을 배웠는지 구체적으로 서술해 주세요. (500자)

**[논리와 레퍼런스로 설득하는 동료 학습]**
42seoul의 동료 평가(Peer Review)와 팀 프로젝트를 진행하며, 감정이 아닌 '명확한 근거'로 의견을 조율하는 소통 방식을 체득했습니다. 
`tini-pong` 팀 프로젝트 진행 당시, 프론트엔드와 백엔드 간의 네트워크 통신 규약(Protocol)을 설계하는 과정에서 팀원과 의견 충돌이 있었습니다. 팀원은 빠른 개발을 위해 무거운 JSON 객체를 통째로 주고받자고 주장했으나, 저는 실시간 액션 게임의 특성상 네트워크 지연(Latency)을 최소화하기 위해 바이너리 기반의 경량 패킷 혹은 최적화된 데이터 구조를 써야 한다고 판단했습니다.
무작정 반대하는 대신, 실제 두 방식의 직렬화(Serialization) 속도와 페이로드 크기를 테스트하여 수치화된 지표를 제시했습니다. 또한, 공식 문서(RFC)와 기존 멀티플레이 게임들의 네트워크 최적화 레퍼런스를 바탕으로 좋은 질문을 던지며 팀원을 설득했습니다. 이를 통해 서로가 코드를 납득할 수 있었고, 결과적으로 지연 없는 실시간 동기화를 이뤄냈습니다. 근거 없는 고집이 아닌, 데이터와 로직을 바탕으로 최선의 합의점을 찾아내는 소통의 가치를 배웠습니다.

## 4. 현재 자신 있게 활용할 수 있는 핵심 역량(프로그래밍 언어, 게임 엔진, AI 활용 능력 등)을 실제로 활용했던 사례와 함께 서술해 주세요. (500자)

**[엔진의 껍데기를 벗긴 코어(Core) 제어력]**
저의 핵심 역량은 엔진이 숨겨놓은 블랙박스에 의존하지 않고, 게임의 심장부인 메모리와 네트워크 로직을 직접 통제하는 '로우레벨 C/C++ 제어력'입니다. 

첫째, **메모리와 시스템 구조 최적화** 역량입니다. C++98 기반의 `ft_irc`와 C언어로 직접 렌더링 수학 연산을 구현한 `miniRT` 프로젝트를 통해, 포인터 연산과 메모리 릭 방어를 완벽히 통제했습니다. 이는 극한의 성능 최적화가 필요한 넥슨의 게임 코어 아키텍처 다루는 데 즉각적으로 활용될 수 있습니다.

둘째, **실시간 네트워크 소켓 통신** 역량입니다. `tini-pong` 프로젝트에서 상용 멀티플레이 플러그인 없이 WebSocket 통신을 직접 설계하여 클라이언트 간 프레임 동기화를 이뤄냈습니다. 

남들이 상용 게임 엔진의 툴(Tool) 사용법을 암기할 때, 저는 엔진이 동작하는 원리와 메모리 할당 방식을 뜯어보고 밑바닥 코드를 짰습니다. 이러한 저만의 하드코어한 기본기가 넥슨의 라이브 서버와 코어 로직을 한 차원 더 견고하게 만들 것이라 확신합니다.
